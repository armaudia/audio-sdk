## Wheel and clean install

The benchmark environment was used read-only as the CPython 3.12 wheel builder;
the wheel was installed into a separate SDK-owned venv without source-tree
imports or runtime dependencies.

```sh
../audio-bench/.venv/bin/python -m pip wheel --no-deps --no-build-isolation \
  --wheel-dir build/python-wheels ./bindings/python
../audio-bench/.venv/bin/python -m venv build/acceptance/python312
build/acceptance/python312/bin/python -m pip install --no-index --no-deps \
  build/python-wheels/audio_sdk-0.1.0-py3-none-any.whl
mkdir -p build/acceptance/tests
cp bindings/python/tests/test_sdk.py build/acceptance/tests/
AUDIO_SDK_LIBRARY="$PWD/build/candidates/macos-arm64-20261114-foundation-07/audio-sdk-0.1.0/lib/libaudio_sdk.dylib" \
  build/acceptance/python312/bin/python -m unittest discover \
    -s build/acceptance/tests -v
```

Wheel SHA-256: `ea4ce935f2ea2938f3b8a5fa243e0952038f0a8bc6f9fc56c0602dd705fda290`.
The four tests passed: ctypes layout sanity, processing/input-shape error,
finite drain and idempotent close, reset epoch, and provider timing metadata.

the SDK module came from the installed wheel. A generated 161-sample PCM16
mono/16 kHz input was processed by both built-in providers. Both output WAVs
were verified to contain exactly 161 frames. Recorded output hashes:

- Speex: `8d1ce44721fd52c9de95e7c045b239b00ee712eaf75c667c92404a6367382466`
- High-pass: `e0cb44f3d0cc1c840dd58449e7816e257d37a46072e0eaf058f5c235a106d924`

the Python test had incorrectly assumed that partial-frame case was valid through
this helper and was corrected to test the supported full-frame process/drain
path. Partial-frame WAV handling was separately exercised by the installed
161-sample example.
